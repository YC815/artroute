3. 一致率用沒取整數的 overall／rank 算；搜尋排名也用沒取整數的值。報告樣本內一致率與留一案例交叉驗證（初始參數沒有擬合任何東西，兩者相同）。

6. 標註樣本工具只產生差異明顯的配對（v3 rank 差距 ≥ 門檻，或現行 vs 規劃器），本機下一輪目標至少 40 組有表態。

### A1 評分 v3＋校正（`matching/score.py`、`bench/likeness.py`、測試）

介面（其他 task 依這個寫）：

```python
SCORE_VERSION = 3
CANVAS_PX = 300.0; SIMPLIFY_PX = 1.5; FULL_CREDIT_PX = 3.0; ZERO_CREDIT_PX = 15.0
DIRECTION_ZERO_DEG = 45.0; WEIGHTS = (0.4, 0.35, 0.25)  # 覆蓋、乾淨、方向
ROTATION_PENALTY = 5.0; ROTATION_REF_DEG = 15.0

@dataclass(frozen=True)
class Score:            # v3（score() 回傳；/match 的 score）
    coverage: int; cleanliness: int; direction: int; overall: int
    exact: float        # 沒取整數的 overall：搜尋排名、校正、剪小刺比較用

@dataclass(frozen=True)
class LegacyScore:      # v1／v2
    coverage: int; cleanliness: int; overall: int

def score(targets, route) -> Score          # v3
def score_v2(targets, route) -> LegacyScore  # 原 score()，數字不可改
def score_v1(targets, route) -> LegacyScore
def rank(score: Score, rotation_deg: float) -> float  # exact − 5 × (θ/15)²，θ 換算到 [-180, 180)
```

- v3 照 P2.5 spec §4.1：目標外框（投影到以外框中心為原點的局部平面，北朝上）長邊 → 300 px；路線同一個轉換後 Douglas-Peucker 1.5 px；`credit(d)` 3／15 px 線性；覆蓋 = 目標每 1 px 取樣到路線的距離；乾淨 = 路線每 1 px 取樣、1 px 格子去重（每格留座標字典序最小的點，與 v2 同理，方向不影響分數），到目標的距離；方向 = 乾淨度取樣點中 d < 15 px 的，路線該處方向與目標最近處方向的夾角（不分正反 0–90°），`max(0, 1 − θ/45°)`，沒有這種點為 0；`exact = 0.4 cov + 0.35 clean + 0.25 dir`（三項用未取整數的值），`overall = round(exact)`。路線方向（騎的先後）不影響分數；用測試釘住（反向、平移整張圖、縮放整張圖分數不變）。
- 效能：一次 v3 在 300 px 畫布上要在 ~30 ms 內（剪小刺會多次呼叫）。點到線段距離用分批向量化（同 v2 的 `_distances`，另回傳最近線段索引）。
- `service.match_shape` 的 score 換成 v3；`MatchResult.score: Score`。
- `bench/likeness.py`：讀 `routes.json.gz`／`labels.json` 的格式（README），重建每條路線的目標（`search.geometry.place`＋封閉補起點）與路線點；`agreement(scorer) -> Report`（有表態配對的一致數、每種配對的一致數：現行 vs V2、現行 vs V3、不同擺放；「差不多」與有表態配對的 rank 差距中位數；留一案例交叉驗證）。比較用 rank（決定 2）、不取整數（決定 3）；同分算不一致。`python -m engine.bench.likeness` 印出報告（findings 用）。
- `tests/test_score_v3_calibration.py`：鎖住實測結果（雲端原型：初始參數＋rank、不取整數 = 10/15）；測試斷言 ≥ 實測值，名稱照 spec `test_score_v3_calibration`。另有 v2 的對照數字（10/15）寫在測試註解。
- v3 單元測試：完美路線 100；平移 3 px 內仍 100、15 px 外為 0；鋸齒（棋盤階梯近似斜線）方向分數明顯低於斜路；多一條支線乾淨度下降、覆蓋不變；同一條街來回騎乾淨度不變；圖形大小不影響分數。
- 既有測試裡依賴 v2 數字的：`test_score.py` 的 v2 測試改呼叫 `score_v2`（語意不變）；`/match` 的整合測試若斷言 overall 門檻，依 v3 重新確認（不放寬安全斷言）。

### A4 剪小刺與小圈（`matching/prune.py`、`matching/turns.py`）— 安全相關

介面：`prune_loops(router, segments, targets, deadline, *, extent_m) -> list[Segment]`，在 `match_shape` 串接之後、`_check_continuous` 之前呼叫（`prune=False` 時不呼叫）。

- 找候選：攤平路線（記段內位置，同 `compose._flat`），用 scipy `cKDTree.query_pairs(r=JOIN_TOLERANCE_M)` 在局部平面找「同一點經過兩次」的 (i, j)，i < j，中間那段（i→j）的弧長在 `MIN_LOOP_M`（2 × `TURN_PROBE_M`，看不到也不值得多一個接點）到 `0.15 × extent_m` 之間。`extent_m` = 目標外框長邊。
- 由短到長逐一嘗試，每剪一次重新找候選。每次嘗試：
  1. 便宜的幾何檢查：剪完在 X 相接的兩點相距 ≤ 1 m（必然，因為 query_pairs）。
  2. 轉彎（**嚴格版**，`turns.rideable_strict`）：轉角 ≤ 30° 放行；> 30° 要 route 檢查通過；`rideable` 視為「量不出來、放行」的情況（原地迴轉：兩個探針落在同一處；一側不到 1 m；探針折回）在這裡一律**不放行**。新接點附近不到 `TURN_PROBE_M` 的既有接點（探針會伸進新幾何）用 `join` 的同一套鄰點重量（重用 `_before_neighbours`／`_after_neighbours`／`_junction_ok`，必要時從 join.py 提出共用函式，不複製）。
  3. v3：`score(targets, 剪後路線).exact ≥ 剪前.exact`（不下降才剪；拿評分判斷這段圈有沒有畫到原圖）。
  順序：先做幾何與不需要 Valhalla 的判斷，再算 v3，最後才呼叫 route（轉彎檢查）。
- 剪法：保留 i 之前（含 i 那一點）與 j 之後（含 j 那一點）；跨段時兩邊各自切片（`_cut` 同 join），中間的段整個拿掉；同一段內就切成兩段（kind、stroke_index 照舊，長度用切片的幾何長度）。所以輸出的點全是 Valhalla 給的點，新接點 ≤ 1 m。
- 期限：每次嘗試前 `deadline.check()`（取消照常生效）；`deadline.remaining()` 低於 `PRUNE_RESERVE_S`（0.3 s）就停止剪、回傳目前結果；最多嘗試 `MAX_PRUNE_ATTEMPTS`（40）次。
- 測試（合成地圖＋真的 Valhalla，`@pytest.mark.valhalla`，`osm_fixture.py` 加新地圖）：
  - 死巷刺：直線旁一條死巷，路線 A→X→B→X→C（用假 segments 從 Valhalla 結果組出來，或讓吸附自然產生）→ 剪掉，輸出相鄰點 ≤ 1 m 或同一結果、`bench.runner.safety_problem` 與 `bad_turns` 都 0；
  - 直線旁的街廓圈：直線上繞一個街廓回到 X → 剪掉；
  - 只能靠繞圈迴轉（單行道街廓、或死路 U 轉）→ 不剪（剪了就是原地迴轉）；
  - 轉角 > 30° 而 Valhalla 不會直接騎的接點（轉向限制或立體交叉，`CROSSING_MAP`／`turn_router`）→ 不剪；
  - 圈畫到原圖（v3 會下降）→ 不剪；
  - 拿掉功能會紅：把 `rideable_strict` 換成 `rideable`、或拿掉 v3 條件、或拿掉鄰點重量時，至少一個測試紅（審查時實際做一次並記錄）。
  - 假 router 的單元測試：候選排序由短到長、跨段切片、期限與最多嘗試次數。

### B1 可騎路網圖（`data/ridegraph.py`、`data/build.py`、`data/checks.py`）

- 來源：修補後的 pbf，篩選 `rideable.is_rideable`。節點：way 端點＋被兩條以上可騎 way 共用的 OSM 節點（第一輪掃描數節點出現次數，numpy `unique`）。邊：兩個節點之間的 way 片段。
- 方向（與 Valhalla 對齊）：`oneway` = yes／true／1 → 只順向；-1 → 只逆向；`junction=roundabout`（沒有 oneway=no 時）→ 只順向；`oneway:bicycle=no` → 雙向；`oneway:bicycle=yes／-1` 優先；`cycleway=opposite*`（含 `cycleway:left/right=opposite*`）→ 雙向（逆向放行）；人行道的 `cycleway=opposite*` 依 `bike_patch` 的註解（只放行逆向）。轉向限制不建（Valhalla 照著走時把關）。拿不準的一律保守（單向），只影響規劃，不影響安全。
- 檔案（build 目錄）：`graph_nodes.npy`（float64 (N, 2) lon/lat）、`graph_edges.npy`（int64 (E, 4)：from、to、幾何起點 offset、旗標 bit0 順向可騎、bit1 逆向可騎）、`graph_lengths.npy`（float32 (E,)）、`graph_coords.npy`（float64 (K, 2)，每條邊的形狀，含兩端點；第 e 條邊是 `coords[edges[e,2]:edges[e+1,2]]`，最後補一個 sentinel）、`graph_cells.npy`（int64，依邊中點落在 0.01° 格子排序後每格的起點，同 `rideable`）、`graph.json`（版本、格網、筆數，最後寫）。讀取：`planner/graph.py` 的 `RideGraph.load(build_dir)` 用 mmap；`region(bbox)` 只讀相關格子的邊（含幾何），建區域的節點重新編號與 CSR（`scipy.sparse.csr_array`，有方向，權重 = 長度）。
- `build_with_patch` 在 `extract_rideable` 之後呼叫 `extract_graph`；記錄耗時與筆數（logger）。`validate_build`：檔案存在、筆數 > 0、索引一致（from／to < N、offsets 單調、最後一個 offset = K、格子 offsets 單調且最後 = E），沒過就是驗證失敗。
- 測試：合成 pbf（`osm_fixture`）：節點／邊數、共用節點切邊、各種 oneway 的方向旗標、禁行（樓梯、快速道路、motorway）不在圖裡、region 只讀需要的格子、validate 抓得到壞檔。

### B2 描形規劃器（`planner/plan.py`）

照 P2.5 spec §6.2。介面：`plan_shape(graph_region, targets, closed_flags, *, deadline, budget_s) -> list[StrokePlan]`；`StrokePlan` 有每段的邊序列（區域邊索引＋方向）、對應的目標取樣範圍、路徑點（lon/lat，邊的幾何串起來）、成本。開放筆畫回傳正反兩個方向。

- 取樣：`L` = 目標外框長邊；`Δ = clamp(0.01 L, 15, 60) m`；記切線；轉角（相鄰兩段夾角 > 30°）標記。
- 候選：每個取樣點在 `min(0.05 L, 250 m)` 內找邊上的投影點，依「距離＋方向差」留前 N = 10。
- 成本（權重放在一個 `PlannerWeights` dataclass，初始值由合成測試定，寫進 spec §8）：平移（≤ 0.01 L 免費，到 0.05 L 二次增加）、方向（每公尺 `1 − cos θ`，有方向性）、轉彎（每個 > 30° 固定成本、180° 迴轉極高）、轉角（目標轉角 ±2Δ 內路線方向變化與目標方向變化的差，0.05 L 內提早或延後不扣）、繞遠（路程超過直線 1.5 倍的部分）。
- 轉移：相鄰取樣點的候選之間在有方向的圖上做距離上限 4Δ 的 Dijkstra（`scipy.sparse.csgraph.dijkstra`，一次多個起點、`limit`），用前驅還原路徑算成本。方向成本以該轉移的目標切線對區域邊重新加權（向量化）。
- 封閉筆畫：起點選最尖的轉角；終點候選必須等於起點候選（對起點前 3 個候選各跑一次取最好）。開放筆畫兩個方向都跑。
- 期限：每個取樣點檢查 `deadline`；超過 `budget_s` 就停，未規劃的部分標成交給 fast。
- 效能：合成城市（`search_city.py` 或新的大棋盤，~2 萬節點）上預設文字大小的圖形 ≤ 1.5 s（雲端量測、寫進 findings；真實路網由本機量）。

### B3 Valhalla 照著走與 `quality: "fine"`（`planner/follow.py`、`routing/router.py`、`matching/service.py`、`app.py`）— 安全相關

- `Router.walk(points)`：`trace_route`、`shape_match=edge_walk`（同樣的 costing 與 `_ensure_matched`）。`follow(router, plan, deadline)`：先 `walk`，失敗用 `trace`（map_snap，取樣 ≤ 15 m、`search_radius` 10 m）；結果與規劃路徑的 Hausdorff ≤ 10 m 才收（`kind="stroke"`）。超過或失敗的那一段，把對應的目標範圍交給現行的 `match_stroke`（fast）。
- 片段之間、規劃與退回 fast 的片段之間一律用 `join.connect`（接點 ≤ 1 m、轉彎檢查、裁切重試、否則斷開）。封閉筆畫照舊 `_stitch_closed`；開放筆畫的反向用規劃器的反向結果（`rematch` 回傳預先算好的反向，不再 `trace_whole`）。
- 之後 compose、剪小刺與小圈（A4）、評分完全照舊。輸出的點全部來自 Valhalla 結果；**任何安全不變式不放寬**。
- `match_shape(..., quality="fast" | "fine", graph=None)`：`fine` 且有 graph 時走規劃器，否則等於 fast。規劃與照著走的預算 `PLANNER_BUDGET_S`（2.5 s，從請求的期限算），超過的部分交給 fast；整個 `/match` 期限仍是 5 s。
- app：每個 worker 快取 current build 的 `RideGraph`（同 `_CurrentRoads`）；`/status` 的 `planner_ready` = current build 有圖。
- 測試（合成地圖、真的 Valhalla；每個場景驗證一件事，P2.5 spec §8）：平行路（目標下方的路中間斷掉、40 m 外有平行路 → 走平行路，不繞出去再繞回來）；轉角（0.05 L 內有角度更像的路口 → 選它）；斜路（棋盤裡一條斜路 → 斜線走斜路）；單行道（`oneway=yes`、`-1`、`oneway:bicycle=no`、`cycleway=opposite` → 輸出絕不逆向，用 `safety_problem` 與逆向檢查）；小刺與小圈（fine 輸出也被剪）；退回 fast（規劃失敗、Hausdorff 超過）；`quality` 不帶時與 fast 完全相同（同一輸入路線逐點相等）；`planner_ready`。拿掉功能會紅：拿掉 Hausdorff 檢查、拿掉 connect 改成直接串、讓規劃器忽略單行道時，至少一個測試紅（審查時實際做）。
