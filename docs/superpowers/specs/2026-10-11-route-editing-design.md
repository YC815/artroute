# 手動微調路線設計

- 日期：2026-10-11
- 狀態：設計已經使用者逐段核可（2026-10-11 本機 session）。§3.4 的簽章範圍在寫 spec 時從「每段一個」改成「整條路線一個」，理由見該節與主 spec §8 第 57 列（可推翻）。
- 上層文件：`2026-10-10-strava-art-design.md`（主 spec）。本文件的設計決策同步寫進主 spec §8 第 56–58 列。
- 排程：P2.5 的 Q3（PR #4）本機驗證之後、Q4 之前（§6.3）。

## 1. 問題與使用者的決定

P2.5 的自動吸附與剪小刺仍會漏掉一些地方。實例：`heart@taipei_daan` 右側 708 m 的繞路，能剪的兩種剪法一個超過圈長上限、一個讓 v3 下降，所以沒剪（`docs/p2-5-likeness-findings.md` §2）。一直調參數總有剩下的案例，讓使用者自己修比較實際。

| 項目 | 決定 |
|---|---|
| 操作 | 剪掉（圈或繞路）、重畫一段、拖曳經過點、復原／重做 |
| 不能直接刪點 | 刪掉中間的點，前後兩點之間就是一條直線，違反「絕不畫直線」。所有操作都是「選一段，叫引擎換一條走法」 |
| 保存 | 微調過的路線自動存成草稿；把圖形移走、重新吸附時，草稿留在「我的路線」 |
| 清除 | 從沒打開過、而且 7 天沒修改的草稿自動刪除；最多 20 份，超過時刪最舊的未打開草稿，全部都打開過就請使用者自己刪 |
| 做法 | A：網站管狀態，引擎負責拼接與驗證整條路線（§3） |
| 排程 | 先做手動微調再做 Q4 |

被否決的做法：

- **B：網站自己拼接，引擎只回傳替換的那一段。** 拼接點的安全（≤ 1 m、轉彎檢查）變成網站的責任，安全不變式要在兩個語言各實作一次，也無法在引擎端驗證最後的路線。
- **C：調整目標圖形再重新吸附。** 剪不掉特定的圈（重新吸附可能換一條完全不同的路），使用者控制不了結果。

## 2. 使用者體驗

### 2.1 進入與離開微調

- 路線出來後，資訊面板有「微調路線」按鈕。進入後圖形**鎖住**（擺放的把手隱藏，地圖拖曳只移動畫面），地圖上的操作都作用在路線上。
- 進入時取消在途的 fast／fine 請求；之後收到的吸附結果一律丟掉。微調過的路線**永遠不會被 fine 或重新吸附蓋掉**。
- 「完成」離開微調：畫面保留微調後的路線，圖形解鎖。之後移動圖形（拖曳、鍵盤、套用搜尋候選、改文字）才會重新吸附；這時微調的路線已經在草稿裡（§4），不會消失。
- 第一次成功的編輯就建立草稿，之後每次編輯都更新它（不等移動圖形才存：分頁被關掉也不會丟）。

### 2.2 操作

| 操作 | 怎麼做 | 引擎做什麼 |
|---|---|---|
| 剪掉 | 選「剪掉」，點路線上的圈或繞路 | 找經過點擊處、最短的「同一點經過兩次」的圈剪掉；找不到就把點到的那段繞路兩端用最短路接起來（§3.3） |
| 重畫 | 選「重畫」，在路線上點兩個點，再選「最短」或「貼圖形」 | 兩點之間換成 Valhalla 最短路，或吸附圖形上對應的那一段 |
| 拖曳 | 抓住路線上任一點拖到新位置 | 抓點前後各 200 m 換成經過放開位置的路 |
| 復原／重做 | 按鈕，或 Ctrl／⌘+Z、Shift+Ctrl／⌘+Z | 不呼叫引擎，網站切回前一個狀態 |

- 等待引擎時顯示進度；引擎拒絕（例如轉彎不能直騎、那裡沒有路）就保留原路線，顯示一行說明，說明可以改用哪個操作。
- 新換上的部分用不同的樣式畫（虛線外框），看得出改了哪裡；GPX 不受影響。
- 復原／重做最多 50 步，只存在記憶體（重新打開草稿從目前狀態開始）。
- 鍵盤：微調中 `Esc` 取消正在選的操作；`H`（隱藏原圖）照常可用。

### 2.3 我的路線

- 側欄「我的路線」列出草稿：縮圖（由路線的點即時畫，不另存圖片）、圖形名稱（文字內容或「圖片」）、公里數、最後修改時間、路網日期。
- 打開草稿：還原圖形來源、擺放與微調後的路線，進入微調模式。打開會把草稿標成「打開過」（§4.2）。
- 刪除：單一刪除要確認；沒有「全部刪除」。

### 2.4 GPX 與舊路網

- 下載 GPX 一律用畫面上的路線：有微調就是微調後的。
- 每週重建路網後，舊草稿照常顯示、能下載 GPX，但標明「這是 X 月 X 日路網上的路線」。要繼續編輯先按「重新驗證」（§3.6）：通過就換成新路網的版本；沒過就標出有問題的位置，請使用者回到自動吸附重做。

## 3. 引擎

### 3.1 端點

`POST /edit` 是無狀態的：每次請求帶著整條路線，回應與 `/match` 200 同形（路線、段落、分數、警告、路網版本，加上簽章），網站沿用現有的顯示與 GPX 程式碼。

```jsonc
// 請求
{
  "segments": [...],            // 上一次 /match、/edit 或 /verify 回應的 segments，原封不動
  "data_version": "20261011T095232Z",
  "route_sig": "…",             // 同一個回應的簽章（§3.4）
  "strokes": [...],             // 使用者放的原圖（與 /match 相同格式）：算分數、「貼圖形」模式用
  "op": { "type": "cut", "at": { "segment": 3, "offset_m": 120.5 } }
     // | { "type": "reroute", "from": Pos, "to": Pos, "mode": "shortest" | "shape" }
     // | { "type": "drag", "grab": Pos, "to": [lon, lat] }
}
```

- 路線上的位置一律用 `{segment, offset_m}`（第幾段、從該段起點量的公尺數），不用經緯度：路線會自己重疊（來回騎的路），用經緯度投影會選錯是哪一趟。網站畫路線時本來就知道點到哪一段。
- 錯誤：`409 stale_data`（`data_version` 不是 current build；網站改走 §3.6）、`422 invalid_route`（簽章不對）、`422` 操作做不到（`not_on_route`、`nothing_to_cut`、`no_route`、`turn_not_rideable`、`no_road`，附繁中說明）、`503`、`504`（5 秒）。任何一項沒過都回錯，**不回半成品**。
- 不在編輯後自動剪小刺：使用者的操作要可預期，不能改到沒點的地方。

### 3.2 安全不變式全部在引擎保證

- 新的部分只來自 Valhalla（`route`，或「貼圖形」時的現行吸附）。保留的部分只切既有的 Valhalla 幾何（在段落內內插的切點也在原本的折線上）。
- 新接點與切點相距 ≤ 1 m（`JOIN_TOLERANCE_M`）；Valhalla 的起訖點吸到別處時，先試切點前後的頂點，仍不行就回 `no_route`。
- 兩個新接點用嚴格版轉彎檢查（`turns.rideable_strict`：原地迴轉、原路折回不放行，≤ 30° 也用 route 量）；離新接點 8 m 內的既有接點用原本的規則重量（與剪小刺相同，主 spec §8 第 43 列）。
- 最後跑一次連續性檢查（`service._check_continuous`）。
- 新換上的段落 `kind` 是 `"edit"`，`stroke_index` 沿用被換掉範圍的筆畫（跨筆畫時為 null）。

### 3.3 各操作的細節

- **剪掉**：用 `prune.py` 的找圈邏輯（相距 ≤ 1 m 的兩點），只看內部包含點擊位置的圈，取最短的。使用者指定的剪法**不套用**圈長上限（外框 15%）、不看 v3 有沒有下降、不受嘗試次數限制；轉彎與連續性照 §3.2。找不到圈時：點到的是 `detour` 段，就把它前後兩端（相鄰段的邊界）用最短路接起來；也不是 detour 就回 `nothing_to_cut`，說明可以改用「重畫」。
- **重畫・最短**：兩個位置之間的路線換成 Valhalla bicycle `route`（兩端各一個 `break` location）。兩點順序依路線上的先後排好（使用者可以先點後面的）。
- **重畫・貼圖形**：兩個位置投影到它們所屬筆畫的目標上（`stroke_index` 不同或為 null 時回 `no_route`，說明改用「最短」），取目標上那一段，用現行吸附（fast）吸附，兩端用 `join.connect` 接回（同 fine 退回 fast 的做法，主 spec §8 第 50 列）。
- **拖曳**：抓點沿路線往前、往後各 200 m（碰到路線頭尾就停）當作範圍，換成 `route(範圍起點 → 放開位置 → 範圍終點)`，放開位置是 `through` location（不會在那裡停下迴轉）。放開位置 50 m 內沒有可騎的路就回 `no_road`。200 m 是初始值：夠拖出一個街廓，又不會動到太遠的地方；本機實測後再調。

### 3.4 防止被塞入假路線：整條路線一個簽章

- 每個 `/match`、`/edit`、`/verify` 的回應多一個 `route_sig`：用伺服器金鑰對「路網版本＋依序的每段（種類、筆畫序號、點）」算 HMAC-SHA256。點先量化成 1e-7 度的整數再編碼（JSON 的浮點數來回是精確的，量化只是讓編碼不受格式影響），回應的點本身不變。
- `/edit` 先比 `data_version`（不是 current build → 409），再驗簽章（不對 → 422 `invalid_route`），通過才做操作。所以就算有人改了請求，引擎也不會把一條直線當路線輸出。
- **為什麼是整條路線、不是每段一個**（核可的第 2 段原本是每段一個）：每段各自簽章時，客戶端仍可以重排、刪掉或重複段落，讓兩段已簽章的路首尾相接（≤ 1 m 的話連續性檢查擋不住），造出沒有檢查過的接點。整條路線一個簽章，未經修改的部分就一定是引擎輸出過的完整路線。復原用的是之前回應的狀態，各自帶著當時的簽章，不受影響。
- 為什麼不改成每次重新驗證：重新驗證要對每段做 `trace_attributes`，慢，而且 `edge_walk` 在共用幾何的 way 之間會配錯、誤判逆向（`docs/p2-5-likeness-findings.md` §4）；簽章是常數時間、沒有誤判。
- 金鑰：`/data/edit-key`（32 bytes 隨機），第一次啟動時以 `O_EXCL` 建立（多個 uvicorn worker 同時啟動只會有一個建成，其他的讀它），權限 600。部署、重啟、換 build 都不變；手動刪掉等於讓所有草稿要重新驗證。測試用暫存目錄。
- `strokes` 不簽：它只影響分數與「貼圖形」吸附的目標，吸附結果照樣經過 §3.2 的檢查。

### 3.5 時間與排隊

與 `/match` 共用同一組 Router 與排隊機制，上限 5 秒（`Deadline`）。`/edit` 只動一小段，預期遠小於 `/match`；本機量中位數與最慢（§6.2）。

### 3.6 舊路網的草稿：`POST /verify`

- 請求：`segments`、`data_version`（舊的）、`route_sig`、`strokes`。舊版本的簽章仍然用同一把金鑰驗（簽章含版本，所以舊簽章只證明「這是引擎在那個版本輸出過的」）。
- 版本與 current 相同：直接回傳（不重算）。
- 不同：在 current build 上檢查每一段——不經過禁行的 way、不逆向（用 bench 安全斷言的同一套邏輯，含合法重現的複查，移到 `matching/` 下共用）、判斷不了算沒過——再檢查連續性與每個接點的轉彎（原本的規則）。全部通過就以新版本重新簽章回傳；沒過回 `422 verify_failed`，附有問題的段落序號，網站把它們標出來請使用者重畫。
- 沒過時不另外回傳「去掉有問題段落」的新版本：那會是斷開的路線，不是一條能騎的路，也無法在上面接著編輯。網站標出有問題的位置，提供「回到自動吸附」（擺放不變，重新吸附後可以再微調）；舊草稿本身保留、仍可下載舊路網的 GPX。

### 3.7 契約

- 新增 `POST /edit`、`POST /verify`；`/match` 回應多 `route_sig`，`segments[].kind` 多 `"edit"`（只有 `/edit`、`/verify` 會回）。只增加，舊網站不受影響。
- 依規定重新產生 `engine/openapi.json`，跑 `cd web && pnpm gen:engine-types`；主 spec §4.7 加「手動微調新增」一節。
- 網站加 `/api/edit`、`/api/verify` 代理（同 `/api/match` 的做法，zod 驗證回應）。

## 4. 草稿

### 4.1 存在哪裡

- 瀏覽器的 IndexedDB（`artroute` 資料庫的 `drafts` store），不上傳。一份草稿約 50–150 KB（路線點），20 份最多約 3 MB：localStorage 的 5 MB 太緊，而且同步 API 會卡住畫面。
- 第一次存草稿時呼叫 `navigator.storage.persist()`（瀏覽器可能拒絕，不影響使用），降低瀏覽器在空間不足時清掉資料的機會。
- 內容：`id`、`createdAt`、`updatedAt`、`openedAt`（null = 從沒從「我的路線」打開過）、圖形來源與擺放（同 `SavedWork`）、`segments`、`data_version`、`route_sig`、`score`。讀取時用 zod 驗證，壞掉的草稿跳過並留在 store（不自動刪，避免版本升級時誤刪）。
- 格式有版本號 `v: 1`；之後改格式要寫升級。

### 4.2 清除規則

- 「打開過」：使用者從「我的路線」打開它。建立草稿的那次微調不算。
- 自動刪除：`openedAt` 為 null，而且 `updatedAt` 超過 7 天。網站載入時檢查一次。
- 上限 20：新建草稿時若已經有 20 份，刪掉 `updatedAt` 最舊的未打開草稿；全部都打開過時，**照樣存**新草稿（不讓使用者的修改消失），並顯示提示請使用者到「我的路線」刪掉幾份。之後每次新建都再提示，直到回到 20 份以下。
- 打開過的草稿不會被自動刪除，只能由使用者刪。

### 4.3 多分頁

- 用 `BroadcastChannel` 通知其他分頁草稿變了，「我的路線」重新讀取。同一份草稿在兩個分頁同時編輯時，後存的覆蓋先存的（`updatedAt` 較新者勝），提示「這份草稿在另一個分頁被修改過」。不做鎖。

## 5. 網站的狀態

- 微調狀態由 `lib/studio/state.ts` 擴充：`mode: "place" | "edit"`、目前路線（含簽章）、復原堆疊與重做堆疊（最多 50）、正在選的操作。
- 吸附排程（`lib/match/scheduler.ts`）在 `edit` 模式不送請求，回來的結果丟掉。
- `lib/storage/drafts.ts`：IndexedDB 的讀寫與 §4.2 的規則（時間由參數傳入，可測）。
- 地圖：路線圖層加點擊與拖曳把手；選操作用 shadcn/ui 的 toggle group。

## 6. 拆 PR、測試、驗收

### 6.1 PR

1. **PR C（引擎）**：金鑰與簽章、`/edit`（剪掉、重畫、拖曳）、`/verify`、契約與 openapi、網站型別重新產生（網站行為不變）。
2. **PR D（網站）**：微調模式、操作、復原／重做、草稿與「我的路線」、GPX、舊路網的提示與重新驗證。

部署順序：引擎先（新欄位與新端點都是只增加），再網站。

### 6.2 測試

安全相關：要真正的審查；每個測試都要做到拿掉功能會紅。

- **引擎・簽章**（純函式）：改一個點、改種類、重排段落、刪掉一段、重複一段、換 `data_version` 都驗不過；同樣的內容換 JSON 格式（空白、浮點數寫法）仍驗得過。拿掉驗證時「改一個點」的測試紅。
- **引擎・合成地圖**（`osm_fixture.py`＋`@pytest.mark.valhalla`），每個場景驗一件事：
  - 剪掉：直線旁的街廓圈被剪掉；超過外框 15% 的圈也剪（使用者指定）；只能靠繞圈迴轉的單行道不剪、回 `turn_not_rideable`；沒有圈的繞路走最短路接起來；點在沒有圈也不是繞路的地方回 `nothing_to_cut`。
  - 重畫：最短模式不逆向騎單行道（`oneway=yes`、`-1`）；貼圖形模式沿目標的路；兩點反著點結果相同。
  - 拖曳：拖到平行路，200 m 範圍外不變；拖到沒有路的地方回 `no_road`。
  - 所有成功的輸出：相鄰點 ≤ 1 m 或來自同一段 Valhalla 結果；新接點通過嚴格轉彎檢查；回應帶的簽章驗得過。
  - 版本：舊版本回 409；`/verify` 在第二張合成地圖（把一條路改成單行）上標出逆向的那段，沒改的路線重新簽章通過。
  - 期限：慢的假 router 讓 `/edit` 回 504，不回半成品。
- **網站**（vitest）：草稿 store（`fake-indexeddb`）的建立、更新、打開、7 天刪除（未打開才刪）、上限 20 刪最舊未打開、全部打開過時照存並提示；復原／重做 50 步上限、新編輯清掉重做堆疊；`edit` 模式不送吸附、遲到的 fine 不覆蓋；GPX 用微調後的路線；`/api/edit` 回應的 zod 驗證。

### 6.3 排程與本機驗收
