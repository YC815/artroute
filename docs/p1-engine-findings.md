## 第一次重建的驗證失敗

第一次重建於 17:38:53Z 開始（程式碼 `ff50cd9`），驗證階段失敗：

```
洲美快速道路檢查失敗：Exact route match algorithm failed to find path: edge_walk algorithm failed …
```

`run_build` 在驗證失敗時會刪除新的 build 目錄，`current` 沒有動，舊的 P0 build `20261010T145928Z` 持續服務。依 brief 沒有修改檢查來讓它通過；先查根因。

### 根因

`Router.edges` 用 Valhalla 的 `edge_walk` 把 route 折線對回路段。`edge_walk` 逐點比對路段形狀，遇到退化的折線就配不出來，丟出例外；而 `_expressway_checks` 一碰到第一個例外就中止整項檢查。在真實資料上看到兩種退化折線：

| 模式 | 條件 | 實測 |
| --- | --- | --- |
| A | 零長度路線：起點與終點吸附到同一個路口，折線只有 `[N, N]` | way 334841526 逆向，`n=2, km=0.0`；nst=0 與預設 nst 都失敗。檢查依 id 排序，這是第一個失敗的方向，正式建置報的就是它 |
| B | `node_snap_tolerance=0` 時，從路口出發的路線開頭重複那個路口點 | way 1075104270 逆向：nst=0 回 26 點、第一個點重複，edge_walk 失敗；預設 nst 回 25 點、成功 |

- 在 scratch build（同一份 pbf，md5 `28cc8b1b…`）上重現，錯誤訊息與正式建置一字不差。
- 18 條洲美快速道路 × 2 方向 = 36 個方向：34 個成功，失敗的就是上表兩個。
- 380 組端點配對（20 個端點）：nst=0 時 edge_walk 失敗 20 組、折線含重複點 72 組；去掉連續重複點後，非零長度路線全部配得出來；零長度路線無論 nst 都失敗。
- Valhalla 3.9.1 原始碼（`route_matcher.cc`、`worker.cc`）：`check_shape` 以頂點數比對，多一個重複點就對不上；第一個起點候選展開失敗會直接 `return false`；`apply_trace_location_defaults` 會強制把 trace 首尾點的 `node_snap_tolerance` 設為 0，所以「讓 `edges()` 使用和 route 相同的 location 選項」行不通。
- 第三種模式 C（單一路段、路口到路口的路線）只在未修補的 tiles 上出現（2 / 380）；修補過的 tiles 是 0 / 380。確切的內部機制沒有完全查清楚，修正不依賴它。

### 修正（`b5f65f6`）

1. `Router.edges`：送進 `trace_attributes` 前先去掉連續重複的點（不連續的重訪 A→B→A 保留）；去完不到 2 點（零長度）就直接回 `[]`，不呼叫 Valhalla。
2. `_expressway_checks`：
   - 零長度路線不算「避開快速道路」的證據，記進 `errors`、不計入 `succeeded`，避免檢查變成空洞通過。
   - 單一路線的 `edges()` 例外改成「該路線的具名失敗」，其他路線照查；仍然 fail-closed，被禁行的 way id 照樣列出。
   - 沒有任何證據、也沒有失敗時才 raise。
3. 沒採用的做法：`walk_or_snap`（退回 `map_snap` 的模糊比對，高架與平面重疊時可能把快速道路配成平面路，讓不安全的 build 通過）。
